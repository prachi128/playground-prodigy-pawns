# Cursor Prompts: The Great Chess Adventure — Backend + Frontend Linking

**How to use this file**

- Run the prompts **in order**, one at a time. Each prompt is self-contained (Cursor sometimes loses context between sessions).
- Before starting, copy `chess-adventure-bots.js` and `chess-adventure-bots.json` into your repo (the prompts assume they live at `backend/data/`).
- After each prompt, review Cursor's diff before accepting. If something references a file/framework that doesn't match your repo, tell Cursor: *"Adapt this to the actual structure you found in Prompt 1."*
- Prompt 1's output (the audit) is the foundation — paste its summary into later prompts wherever you see `[PASTE AUDIT SUMMARY]`.

## Prompt 4 — Chess engine service (bots that actually play at kid level)

```
Context: /backend Express app. Bots range from rating 100 (plays almost
randomly, hangs pieces) to 1600 (solid club player). Stockfish's weakest
skill level still plays ~1300+, so low-rated bots need artificial mistakes.
The data module already provides ratingToEngineConfig(rating) returning:
{ skillLevel, searchDepth, moveTimeMs, randomMoveChance, hangPieceChance }.

Build backend/src/services/engineService.ts:

1. Dependencies: install chess.js (move legality/game state) and stockfish
   (WASM build of Stockfish that runs in Node). If the stockfish npm package
   is problematic in Node, use a child_process wrapper around a stockfish
   binary with a clear TODO comment and a config flag for the binary path.
2. Engine pool: manage a small pool (2–4) of Stockfish instances via UCI so
   concurrent games don't fight over one process. Expose:
   getBestMove(fen, {skillLevel, searchDepth, moveTimeMs}) → Promise<uciMove>
   Set "Skill Level" UCI option per request; use "go depth N" or
   "go movetime M" per config.
3. Personality mistakes — implement pickBotMove(fen, engineConfig):
   a. roll = Math.random()
   b. If roll < randomMoveChance → return a uniformly random legal move
      (via chess.js), EXCEPT never play a move that gives away the bot's
      king safety trivially: filter out moves that allow checkmate-in-1 for
      the opponent ONLY when rating >= 200 (below that, pure random is fine
      and fun for tiny kids).
   c. Else if roll < randomMoveChance + hangPieceChance → prefer a
      "hanging" move: generate legal moves, find ones that move a piece to
      a square attacked by the opponent and not defended (use chess.js
      attack info; a simple isAttacked check on the destination square is
      acceptable v1). If any exist, pick one at random; else fall through.
   d. Else → return Stockfish's best move using the config.
4. Special case: at rating >= 800, randomMoveChance is ≤ 0.05 and
   hangPieceChance is 0, so play is essentially clean engine chess — make
   sure the code path is efficient (skip the hanging-move scan when
   hangPieceChance === 0).
5. Export: pickBotMove(fen, botId) that internally does
   getBotWithEngine(botId) and applies the above.
6. Tests: add a spec that (a) plays 20 moves as Benny (rating 100) from the
   start position and asserts no crashes and all moves legal, (b) asserts
   Goldscale (1600) never triggers the random/hanging branches, (c) asserts
   pickBotMove rejects an invalid FEN with a clear error.
```

## Prompt 5 — Game session API

```
Context: /backend Express app with engineService.pickBotMove(fen, botId)
and adventureService. Build stateful game sessions the frontend can play
against.

1. Storage: in-memory Map<gameId, GameSession> for v1 (add a storage
   interface so a DB/Redis can swap in later). GameSession:
   { gameId, botId, playerColor: 'w'|'b', fen, moveHistorySan: string[],
     status: 'active'|'player_won'|'bot_won'|'draw',
     createdAt, updatedAt }
2. Endpoints:
   POST /api/games
     body: { botId, playerColor? } (default playerColor 'w')
     → creates session at the standard start position. If playerColor is
     'b', immediately make the bot's first move.
     → respond: { gameId, fen, playerColor, botMove?: {from,to,san},
       dialogue: bot.dialogue.greeting,
       bot: {id, name, avatar, rating, themeColor of its world} }
   POST /api/games/:gameId/moves
     body: { from, to, promotion? }
     → validate the player's move with chess.js (illegal → 400 with
       {error, legalMovesForFrom?}).
     → apply it; check game over. If game continues, get the bot reply via
       pickBotMove, apply it, check game over again.
     → respond: { fen, playerMove: {san}, botMove?: {from,to,san},
       status, gameOver?: { result: 'player_won'|'bot_won'|'draw',
         reason: 'checkmate'|'stalemate'|'insufficient'|'threefold'|'fifty',
         dialogue } }
       where dialogue = bot.dialogue.playerWins on player_won,
       bot.dialogue.playerLoses on bot_won, pickDrawLine() on draw.
   GET /api/games/:gameId → current session state.
   POST /api/games/:gameId/resign → status 'bot_won', but dialogue must
     STILL be the encouraging playerLoses line (this is a kids' platform —
     never a negative message).
3. Guardrails: reject moves when status !== 'active' (409). Reject a second
   in-flight move for the same game (simple per-game lock/flag).
4. Cleanup: evict sessions older than 24h (setInterval sweep).
5. Add supertest specs: full game where the test plays scholar's-mate-ish
   moves vs Benny; resign flow returns the encouraging line; illegal move
   returns 400.
```

## Prompt 6 — Player progression & unlock system

```
Context: /backend Express app. The adventure is a quest map: 50 bots, six
worlds, levels unlock sequentially. The frontend audit
(docs/frontend-audit.md) shows where the UI expects progress data — match
those shapes.

1. Model (in-memory Map<playerId, Progress> behind a storage interface):
   Progress: {
     playerId,
     currentLevel: number,          // highest unlocked level, starts at 1
     stars: Record<botId, 0|1|2|3>, // 3=win, 2=draw, 1=played, 0=locked
     defeatedBosses: string[],
     lastPlayedAt
   }
2. Rules:
   - Beating bot at level N unlocks level N+1.
   - A draw or loss does NOT unlock the next level but records stars
     (draw=2 if higher than current, played=1 minimum once a game finishes).
   - World unlock is derived: a world is unlocked if its first bot's level
     <= currentLevel. Include Wizzy's world narration.intro in the payload
     the first time a world unlocks (flag: newlyUnlockedWorld).
3. Endpoints:
   POST /api/players            → { playerId } (uuid; frontend stores it)
   GET  /api/players/:playerId/progress
        → { currentLevel, stars, defeatedBosses,
            worlds: [{id, unlocked, completedCount, botCount}],
            nextBot: summary of getBotByLevel(currentLevel) }
   Progress updates: do NOT add a public "mark as won" endpoint (kids/
   parents could cheat-click). Instead, update progress inside the game-over
   branch of POST /api/games/:gameId/moves and /resign — pass playerId when
   creating a game (POST /api/games body gains optional playerId).
4. On game over, include in the response:
   { progress: { unlockedLevel?, starsEarned, newlyUnlockedWorld?:
     {id, name, narrationIntro} , adventureComplete?: boolean } }
   adventureComplete=true when Goldscale (level 50) is beaten — also include
   ADVENTURE.guide.finale text in the payload.
5. Specs: winning level 1 unlocks level 2; losing level 1 does not; beating
   level 8 (Grandpa Oak) flags newlyUnlockedWorld = candy-kingdom; beating
   level 50 returns adventureComplete with the finale text.
```

   REACT_APP_API_URL — pick the right one for this stack; default

     Wizzy's speech bubble if the UI has one)

## Prompt 9 (optional polish) — Per-bot personality quirks on the board

```
Context: /backend engineService currently differentiates bots only by
rating-derived config. Add light per-bot flavor so play styles match their
descriptions. Keep it simple and safe — quirks BIAS move choice, they never
produce illegal moves and never apply above the bot's mistake budget.

1. Add an optional `quirk` field per bot in a NEW file
   backend/src/config/botQuirks.ts (do not edit the data files):
   { botId: { type, weight } } where type ∈
   'prefers_knights' (Buzzby, Sir Choco Chip),
   'mirrors_player' (Polly — copy the player's last move mirrored when
     legal, else normal logic),
   'pawn_pusher' (Mushroom Mel, Marsh Mellow — bias toward pawn moves),
   'early_king_march' (King Kandy — bias king moves in the middlegame),
   'trader' (Boop, Roomba Rex — bias captures that trade evenly),
   'rook_lover' (Cannonball Carl, Saturn Sue — bias rook moves to open
     files).
2. In pickBotMove, after the random/hanging rolls miss, apply the quirk with
   probability `weight` (e.g. 0.35): filter legal moves matching the quirk;
   if non-empty, ask Stockfish to choose the best among ONLY those (use
   `searchmoves` in the UCI `go` command); else fall back to normal best
   move. This keeps quirky bots playing their character without becoming
   accidentally much weaker or stronger.
3. Add specs: Polly mirrors a mirrorable opening move; Buzzby's first 6
   moves include at least one knight move in 90%+ of 50 simulated games.
```

## Quick reference — response shapes the frontend will receive

| Action | Key fields |
|---|---|
| Start game | `gameId`, `fen`, `dialogue` (greeting), `bot` summary |
| After each move | `fen`, `botMove {from,to,san}`, `status` |
| Game over | `gameOver.result`, `gameOver.dialogue` (win/lose/draw line), `progress.unlockedLevel`, `progress.newlyUnlockedWorld`, `progress.adventureComplete` |
| Progress | `currentLevel`, `stars`, `worlds[].unlocked`, `nextBot` |
